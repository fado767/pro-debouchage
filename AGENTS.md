# AGENTS.md

*The working rules for this folder. Any tool with access to the folder reads this first. Created 2026-08-22, the kickoff session, modelled on the taxi business rules (`../taxi-business/AGENTS.md`) and deliberately smaller. Procedure lives in the three skills, facts live in the owner files below, this file only carries rules.*

## 1. The project, in three sentences

Pro Débouchage is a 24/7 drain-unblocking, sewer cleaning, camera inspection, septic emptying and flooded-cellar pumping service based in Vilvoorde, serving Brussels and the towns 40 to 60 km around it, in French and Dutch. It is owned by Roro (Fady's cousin), the work is done by Afrim, and it is a client of Fady's agency (fady.be, hi@fady.be) for ONE converting landing page plus Google Ads that make the phone ring. It is a single client with its own site, not a template business: nothing here is reused across clients, and nothing from the taxi business is edited from here.

## 3. What each folder is for

- `STATE.md` what is true today, rewritten in place, budget 14 KB. Every session reads it first.
- `NOW.md` what is open, one line each, owner-tagged `[Fady]` / `[Claude]` / `[Roro]` / `[clock: date]`, budget 8 KB. A closed line moves to `LOG.md` in the same session.
- `HANDOFF.md` the note the last session left for the next one, overwritten at every close, budget 4 KB.
- `DECISIONS.md` dated decisions, append-only, no budget on the file, max 5 lines per entry.
- `LOG.md` dated, append-only, one entry per session, no budget on the file, but ONE entry stays under about 2,500 bytes (five short lines). Log changes, not activity.
- **Budgets are in BYTES, not lines** (changed 2026-08-30). A line cap measures nothing here, because these files run one long paragraph per line: `STATE.md` sat at 27 percent of its old 120-line cap while costing 11.9 KB to read. What a session pays for is bytes read. The three budgets above are the real sizes of 2026-08-30 plus roughly 20 percent headroom. Check with `wc -c STATE.md NOW.md HANDOFF.md`. The same reason sets the per-entry limit on `LOG.md`: the file is 148 KB, twelve of its entries pass 2,000 characters and one is 6,162, which is why `/pro-orch` can only afford to read the last entry.
- `playbook/` the curated knowledge, small files read on demand: `business-brief.md` (the client facts), `accounts.md` (every account, who owns it, how we reach it, NEVER a password), `launch-plan.md` (the gated plan to go live), `landing-page.md` (the page spec and copy decisions), `ads-program.md` (the campaign and its routine), `invoicing-flow.md` (how a job becomes a bill: what Roro sends Steph, the invoice and credit-note rules, Peppol), `separation.md` (how fady.be keeps clients apart), `site-companion.md` (the page section by section with answers to Roro's likely questions, a reference doc, uncapped).
- `research/` raw agent reports, dated, read-only reference, catalogued in `research/INDEX.md`. Never the owner of a fact: when a research fact becomes a decision, it moves into a playbook file or `DECISIONS.md`.
- `assets/raw/` what Roro sent, untouched. `assets/prepared/` what we made from it.
- `design/site-source/` THE page source (the one locked design, 2026-08-26): template, copy FR/NL/EN, styles, CGV and privacy modules, build script, fonts; its README carries the exact build and deploy commands. `site-v1/` is the build output, generated by `node design/site-source/build.js`, never edited by hand. (Locked 2026-08-26 on Fady's yes; the retired first page and the v2 pack moved to `_archive/2026-08-26-lock-in/`.)
- `_archive/` closed history, unchanged.
- `to-delete/` the waiting room for superseded files (Fady, 2026-08-26). A replaced file that is not worth keeping is MOVED here in a dated subfolder, never deleted in place and never left lying next to the live one. Nothing reads from it. **Only Fady empties it.** Keep-worthy history goes to `_archive/` instead.
- `.claude/skills/` the three routines `/orch`, `/orch-mid`, `/eof` (renamed from `/pro-orch`, `/pro-orch-mid`, `/pro-eof` on 2026-09-04, the HQ consistency pass, so every venture folder answers to the same three words; the procedure inside them is unchanged).

Added 2026-08-28, named here and put on the backup whitelist 2026-08-30 after an audit found the enforcement layer had no cloud copy while the rules it enforces did. Since 2026-09-04 the hooks, the script, the two `.cmd` files and the three routine skills are the shared kit every venture folder carries (`../fady.be/kit/README.md`); the `.js` hook files became `.cjs` the same day, and the em dash hook now checks the text a tool writes instead of the whole file.

## 5. The rules that never bend

1. **Never fake anything.** No fake reviews, no fake counters, no unproven claims ("20 years", "1M users", "97%") in any copy. We claim only what Roro confirms and what we can show.
2. **The client owns what matters and is never locked in:** his domain, his Google account, his Business Profile, his Ads account and its billing, his reviews. The agency is a manager on them, never the owner.
3. **No ad-ROI promises** to Roro before real numbers exist.
4. **The Business Profile is a gate:** no address or name goes onto Google before the address question (section 1 of `playbook/launch-plan.md`) is settled.
5. **One live page, one design.** Changes are made in the `design/site-source/` source, rebuilt and redeployed. Nothing is edited on the live host by hand.
6. **`../taxi-business/` is read-only from here.** We learn from it, we never change it, and its accounts are never reused for this client (see `playbook/separation.md`).

## 6. Writing rules

- **No em dashes**, ever, in anything new: chat, files, copy, scripts, WhatsApp drafts. Commas, full stops or brackets instead.
- **Customer-facing copy is French first and Dutch second, simple words, short sentences**, no marketing fog, no unproven claims. Both languages ship together.
- **Copy is written to convert, never merely translated** (Fady, 2026-08-24). Anything customer-facing, new or changed, matches the page's established voice per language (FR spoken "on", everyday Flemish, EN with contractions), speaks to the customer in their situation, and sells the call. FR, NL and EN each carry the same promise as native persuasive copy; a literal word-for-word translation is a bug.
- **Anything for Roro is simple English**, WhatsApp length, one question per line when asking.
- **Long numbers digit by digit** in anything meant to be read aloud (phone numbers, enterprise numbers).
- Prices in euros, VAT stated.

## 7. Working rules for any tool that touches files

- Edit the live file directly. Git history is the backup. No `.bak` copies.
- **TWO SESSIONS MUST NEVER BE WRITING AT THE SAME TIME, and "only one window is open" no longer proves it.** Sessions on this folder are now started and answered from the phone and from the cloud as well as from this machine, and Fady REPLIES from his phone, so a phone session drives real edits: the same human can be driving two writing sessions from two devices, hours apart, without either one knowing. The guard that actually works is cheap: **every session re-reads `STATE.md`, `NOW.md` and `HANDOFF.md` immediately before its first write of a stretch of work, not only at session start.** A session that has been idle, or that may have been resumed on another device, assumes the files moved under it. When the live state files have changed since the session last read them, it does NOT overwrite: it re-reads, merges its change onto what is there now, and says so. Inside one session, agents that edit files still run one at a time; read-only agents may run in parallel. Never run Cowork and Claude Code on this folder at the same time. (Corrected 2026-08-30 on Fady's yes.)
- **Sandboxed tools (Claude Code, Cowork, agents) never run git and never run `save-to-cloud.cmd` or `first-time-setup.cmd`.** They edit files, then stop. Fady double-clicks the backup himself, and only when something changed.
- **Live state files are rewritten in place** (`STATE.md`, `NOW.md`, `HANDOFF.md`, the playbook files). They carry no dated correction notes: the change is logged in `LOG.md` and git keeps the old text. Only `LOG.md` and `DECISIONS.md` are append-only history. This is the one deliberate difference from the taxi rules, chosen on 2026-08-22 so the files stay small enough to read whole.
- **Size caps are rules, not wishes, and they are byte budgets** (section 3: `STATE.md` 14 KB, `NOW.md` 8 KB, `HANDOFF.md` 4 KB). Check with `wc -c` on the file. When a file passes its budget, the same session trims it (closed lines to `LOG.md`, spent facts out of `STATE.md`) before adding anything. `LOG.md` and `DECISIONS.md` stay append-only with no budget on the file, but one `LOG.md` entry stays under about 2,500 bytes.
- Never store passwords, recovery codes, API tokens or card numbers in any file. `playbook/accounts.md` says WHICH account and WHO owns it, never HOW to get in.
- No customer personal data in the files beyond what the page itself shows.
- **After any edit to the page source, rebuild and check the result** (styles included) before calling the work done; a broken build or stale CSS ships silently otherwise. (Added 2026-08-24 on Fady's yes.)
- **Image picks are made from VIEWED images, never from filenames.** Crops of the same photo hide under different names; two duplicates shipped on 2026-08-24 because files were judged by name. Open and look before choosing, deduplicating or deleting. (Added 2026-08-25 on Fady's yes.)
- **A CHANGED IMAGE ALWAYS SHIPS UNDER A NEW FILENAME.** Replacing an image in place leaves the old bytes on the Cloudflare edge for up to 24 hours (`cf-cache-status: HIT`, max-age 86400), so the deploy succeeds, the new file is on the host, and the live page still shows the old picture. Bump the name instead (`van-2.jpg`, `afrim-avatar-2-*`), point the build at it, and move the replaced set to `to-delete/`. This bit twice on 2026-08-28, the og-banner and Afrim's avatar. (Added 2026-08-28 on Fady's yes.)
- **IDENTITY DOCUMENTS AND PERSONAL PAPERS ARE HANDLED OUTSIDE THIS FOLDER, redacted copies included.** No ID card, passport, residence permit, driving licence or similar personal document is ever saved anywhere under this folder, not even briefly and not even with the photo and the national number blocked out. `assets/` is on the backup whitelist, so a file dropped there is one backup run away from living in the version history forever, and the back of a Belgian eID carries the rijksregisternummer. Roro's ID card landed in `assets/raw/` as Front.jpg and Back.jpg on 2026-08-30 during the Google Ads affiliation task and was caught by luck, before any commit. Work on such documents from somewhere outside the folder, and record in the files only that it was done, never the document. (Added 2026-08-30 on Fady's yes.)
- **Browser work runs ONE agent at a time, and the agent opens the right Chrome profile itself** via `chrome.exe --profile-directory="..."` using the profile map in Claude's memory (chrome-profile-map), then verifies which account fronts before reading anything. Never ask Fady which browser, never run two browsing agents in parallel: on 2026-09-01 two parallel agents grabbed the same browser and closed and navigated each other's tabs. (Added 2026-09-01 under the same-day rule delegation. Refined 2026-09-04: section 14 is the shared wording, with the helper script `node .claude/scripts/chrome.cjs open "Pro Debouchage"` and the one honest limit found by test that day: opening the profile by command works, connecting the extension in a freshly opened window still takes one side-panel click by Fady.)
- **VERIFY THE RESULT, NEVER THE SUBMISSION.** After anything is submitted to an external surface (a Google form, a verification flow, a dashboard action), the page is RE-READ and the RESULT confirmed before the outcome is written into any file. A submit is not an outcome. On 2026-08-30 the Google Ads "Confirm your affiliation" ID upload was filed as unconfirmed with a verdict in 1 to 10 days, because no success screen appeared; it had in fact been ACCEPTED the same day, and the only place that shows it is the Completed tasks list. Fady found it, the session did not. Many Google flows never show a success screen at all, so "nothing happened" is evidence of nothing: go and look where the answer actually lives. (Added 2026-08-30 on Fady's yes.)
- **A FACT-SYNC AUDIT RUNS AT LEAST ONCE A WEEK.** The live state files are read every session, so they stay honest. The `playbook/` files are read ON DEMAND, so nothing forces them to be re-read and they rot silently. On 2026-08-30 `STATE.md`, `NOW.md` and `HANDOFF.md` were all accurate and clean while roughly SEVENTEEN facts in `playbook/` were stale, two of them account-critical (`accounts.md` said the ad campaign was paused when it had been running for two days, and named the wrong payment card) and one of them the name of the customer review in the script that gets read aloud to Roro. So: a READ-ONLY agent cross-checks every `playbook/` file against `STATE.md`, `NOW.md`, `DECISIONS.md` and the live site source, and reports every contradiction with file and line. It runs at least weekly (the natural slot is the Monday `/pro-orch`, alongside the weekly ads check) and always after a session that changed an account, a price, a name or a live surface. It reports, it never fixes on its own: findings are fixed in the same session or filed in `NOW.md`, never left in chat. The cheap heuristic when reading anything: a fact that appears in more than one file is a candidate for drift, and section 4 names its one owner. (Added 2026-08-30 on Fady's yes.)

## 8. Logging (every session)

Fady never logs anything himself. The moment something loggable happens (done, decided, created, spent, promised, approved, a fact changed) it is filed in the same session: `LOG.md` for what happened, `NOW.md` for what is open, `DECISIONS.md` for decisions, `STATE.md` when what is true changed, `playbook/accounts.md` when an account was created or access changed. Every session ends with one line: what was logged and where, or "Nothing to log this session."

## 9. Close it, or file it, never leave it in chat

No task is deferred to "later" inside a conversation. It is done now, or it is a line in `NOW.md` with an owner, or a line in `DECISIONS.md`. A task that exists only in chat prose does not exist. A decision Fady makes in chat is written to the file it belongs to the moment it is made.

## 10. How a day runs

- `/orch` (until 2026-09-04: `/pro-orch`) starts the day: it reads `STATE.md`, `NOW.md`, `HANDOFF.md` and the last `LOG.md` entry, checks them against each other in one line, gives the overview (**MINE** / **RORO'S** / **A CLOCK'S**), proposes the day's plan with reasons, then waits for Fady's go.
- `/orch-mid` (until 2026-09-04: `/pro-orch-mid`) resumes the same day from `HANDOFF.md` without repeating the overview.
- `/eof` (until 2026-09-04: `/pro-eof`) closes the day (at any hour, a morning close is normal): bullet-point plain-English summary, logs filed, `HANDOFF.md` rewritten, file sizes reported. Improvements to rules and skills are APPLIED directly, dated, when they only change how Claude and the files work internally; they go to Fady only when they change what he does, sees or decides (Fady, 2026-09-01).
- **Fan-out mode is the standard:** the session fans work out to subagents on **Opus 5** by default (Fable 5 only when Fady says so or the task truly needs it). **The orchestrator NEVER executes a task itself, browser clicks included** (Fady, restated 2026-08-29 after the session did the Ads work itself): it plans, briefs agents, verifies their claims and files the results. Execution always goes to a subagent on a good cheaper model; when a task needs something only the session can do (an AskUserQuestion pick, a permission grant), the session gets that one piece and hands the task back to an agent. Before agents fire, the session explains each agent's job in plain English so Fady's yes is informed. Anything that is Fady's call comes as an AskUserQuestion widget with the essentials INSIDE the widget, because Fady sees the widget, not the prose above it.
- **Do the work by default:** anything that needs no payment, no credentials and no decision that is truly Fady's is done by the session (browser included). Money, passwords, account-level agreements, access grants and anything that touches a live client surface come to Fady first. The permission classifier refuses access-grant clicks for agents and the main session alike: plan those as Fady's clicks upfront (inventory by an agent, Fady clicks, read-only verify by an agent).
- **Fady reacts to the work, he does not read explanations** (Fady, 2026-08-26): build it, deploy it, hand him the link and a few lines. No account of what was touched and why. Anything that is genuinely his decision comes as an AskUserQuestion widget with the context inside it; everything else is just done, cleanly, and verified before he is told it is ready.
- **Continuity is the session's job to call:** when context grows long enough that quality or cost suffers, say so unprompted, rewrite `HANDOFF.md`, and the next session starts with `/orch-mid`.
- **A design round is done only when the change is deployed to the preview and verified there.** The deployed preview is the ONLY review surface. (Added 2026-08-24 on Fady's yes; the canvas-artifact caveat it once carried died with the v2 pack at the 2026-08-26 lock-in.)

## 11. Automation and improvement mindset

The end goal is a business mostly run by agents, with Roro's setup kept dead simple. For every task ask two things: can this be automated, and did this session reveal a better rule, file or routine? Say so in one line so Fady decides. A skill that misfires is fixed the same day it is used.

## 12. When you are unsure

Say "not in the files" instead of guessing. Never invent a fact, a number, a price or a client detail. Say plainly when an idea is your own rather than something the files decided. Ask Fady one clear question rather than choosing for him on anything that spends money, touches a live surface, or changes a rule.

## 13. Backup and git (the shared rule, kit 2026-09-04)

*Section 7 already carried these rules since 2026-08-22; this is the shared wording every venture folder carries, so the HQ can compare them. Where the two differ, the stricter one holds.*

- The backup is a private GitHub repo under Fady's account (`fado767/pro-debouchage`, connected 2026-08-30). `save-to-cloud.cmd` backs the folder up and only says SAVED when GitHub provably matches this computer. Only Fady runs it, by double-click, and only when something on disk changed. A session's closing block reminds him in one line; the reminder is never an open item. (The spent `first-time-setup.cmd` moved to `to-delete/2026-09-04/` on Fady's ask; section 3's mention of it is history.)
- Sandboxed tools (Claude Code, Cowork, agents) never run git, not even read-only, and never run the two scripts. `.claude/hooks/deny-git.cjs` enforces it. Reason on record: a session's read-only git command left a lock file that silently blocked Fady's backup on 2026-08-15 (taxi business).
- `.gitignore` is a WHITELIST: it names what is backed up. Machine-local and generated files stay out (`.claude/settings.local.json`, `.claude/launch.json`, `.claude/hooks/state/`, `.claude/worktrees/`, `node_modules/`). Whoever adds a root folder that must survive adds it to the whitelist in the same session.
- Never run `save-to-cloud.cmd` while a session is actively writing files: the script clears a leftover lock as a last resort, and doing that mid-write is how the taxi repo corrupted on 2026-07-07.
- Edit the live file directly; git history is the backup, no `.bak` copies.
